# Building the Truecairn client — reproducibly

The security promise (`docs/CRYPTO.md`, `SECURITY.md`) is only worth as much as
your ability to check that **the JavaScript the server sends your browser is the
JavaScript built from the source you can read**. This document is how you do
that: build the client yourself from a tagged commit and match its hash to the
bytes the live site serves.

The web client (`apps/web`) and the crypto packages it bundles (`packages/crypto`,
`packages/keys`, `packages/client-crypto`, `packages/ceremony`, `packages/shared`)
are the reproducible, buildable core. Everything that touches a plaintext secret
lives there and runs on your device.

## Toolchain (pin these)

| Tool | Version | Where it's pinned |
|---|---|---|
| Node.js | 22.x (LTS) | `.github/workflows/ci.yml` (`node-version: 22`); `package.json` `engines` requires `>=20`, CI builds on 22 |
| pnpm | 10.33.0 | `package.json` `"packageManager": "pnpm@10.33.0"` — `corepack` reads this |
| Dependencies | exact | `pnpm-lock.yaml` (committed); build with `--frozen-lockfile` |

The lockfile is the anchor. `--frozen-lockfile` makes the install fail rather
than silently resolve a different dependency tree, so two people on the same
commit install byte-identical `node_modules`.

## Reproducible build

> **No release has been tagged yet** (checked 2026-08-09: zero tags, zero
> releases in either repository). Earlier revisions of this document opened with
> `git checkout v1.0.0`, which does not resolve — it sent a verifier to a dead
> ref on the first command. Until a tag exists, verify the published head and
> compare it against the `Source commit` shown on `/security/build`; if those two
> commits differ, expect the digests to differ too, and that difference is not
> evidence of anything on its own.

```bash
# 1. Check out the commit you want to verify. Use the published head, or the
#    commit /security/build names if the mirror has caught up to it.
git log -1 --format=%H            # note what you actually built

# 2. Pin the package manager the repo declares (no global pnpm drift).
corepack enable
corepack prepare pnpm@10.33.0 --activate

# 3. Install the exact locked dependency tree.
pnpm install --frozen-lockfile

# 4. Build only the web client and its workspace deps.
pnpm --filter @truecairn/web build
```

The output is `apps/web/dist/` — a static bundle (hashed asset filenames,
`index.html`, the libsodium WASM). That directory is the whole client; the API
serves exactly these files when `WEB_DIST_DIR` points at them (`docs/23`).

### Hash it

```bash
# One digest over the whole tree, order-stable, for a release-to-release compare.
find apps/web/dist -type f -print0 | sort -z | xargs -0 sha256sum \
  | sha256sum | cut -d' ' -f1

# Or per-file, to see exactly which asset differs if a compare fails.
find apps/web/dist -type f -print0 | sort -z | xargs -0 sha256sum
```

Publish the tree digest in the release notes for each tagged release. Anyone can
re-run the four build steps above and confirm they land on the same digest.

## Matching the build to the live site

The served client is same-origin under the deployment host. To check the running
site against your local build:

1. Load the site, open the browser's network panel, and note the hashed asset
   filenames it fetches (e.g. `index-<hash>.js`, the WASM).
2. Compare those files to the ones in your `apps/web/dist/` — the content hash in
   the filename is Vite's own digest of the bundled module, so a matching name is
   already strong evidence; `sha256sum` the downloaded file against the local one
   to be certain.
3. A mismatch means the served client was built from source you have not read —
   treat that as a finding and report it (`SECURITY.md`).

## Why a bit-for-bit match isn't guaranteed (and what to do)

Vite/esbuild output is deterministic **for a fixed toolchain**, but a different
Node minor, a different OS, or a different pnpm can perturb bytes without changing
behaviour. If your local digest doesn't match a published one:

- Confirm Node is 22.x and pnpm is exactly `10.33.0` (`node -v`, `pnpm -v`).
- Confirm `pnpm install` used `--frozen-lockfile` and reported no lockfile change.
- Diff **per-file**: a single differing asset localises the cause; identical asset
  count and near-identical sizes point at toolchain skew, not tampered source.

## Provenance (shipped 2026-07-25)

Every build now emits `dist/build-manifest.json`: a SHA-256 per shipped file plus
one `bundleDigest` over the sorted `(path, hash)` pairs, so a human compares **one**
short string rather than a table of ninety-odd. It is generated by
`scripts/build-manifest.mjs`, which runs as part of `pnpm --filter @truecairn/web
build`. The manifest is **not** self-covering — a file cannot contain its own hash —
so the trust anchor is the CI attestation over `dist/`, never the manifest alone.

`.github/workflows/release.yml` is written and public, but **has never been
triggered** — there are no `v*` tags, so nothing below has produced an artifact
yet. Read this section as the design of the release path, not as a description
of artifacts you can go and fetch. When it runs, it:

1. builds on pinned Node 22 + the `packageManager` pnpm (the digest is only
   comparable across builds if the toolchain is);
2. **builds twice and fails the release if the digests differ** — `/security/build`
   tells users they can rebuild from source and compare, so that has to stay true,
   and a release is the wrong time to discover it isn't;
3. attaches a signed **SLSA build provenance** attestation over `dist/**` via
   `actions/attest-build-provenance`;
4. publishes the bundle + manifest as release artifacts.

The public `/security/build` page shows the digest of the bundle the visitor is
actually running, alongside its source commit and release tag.

**What this is worth, stated the way the page states it.** It does not eliminate the
structural weakness of browser-delivered end-to-end encryption: the code computing
and displaying the digest is served by the same origin as the bundle it describes,
so a fully compromised origin could doctor both. Nothing served same-origin can fix
that. What changes is the *economics* — a tampered bundle must now survive comparison
against an artifact signed by a build that ran from public source on infrastructure
the attacker doesn't control. Silent, targeted, deniable tampering becomes tampering
that leaves evidence. Overstating this would be worse than shipping nothing, because
it converts an honest limitation into false assurance; `/security/build` and the
tests in `apps/web/tests/public-pages.test.tsx` both pin that wording.

**The chain is partly closed — read this before quoting the claim (revised
2026-08-09).** The source is published at
`github.com/M-Romdhani/truecairn-public` — a curated mirror carrying the
`apps/`, `packages/`, `docs/` and CI needed to rebuild and verify, with
internal-only material held back (deployment topology, the recovery drill, the
audit-scope weakness table, legal posture, the build log). `REPO_URL` in
`apps/web/src/site/links.ts` points at it, which lights up both the footer source
link and the rebuild-and-compare instructions.

Two links in that chain are open, and this document previously claimed both were
shut:

1. **No signed attestation exists.** `release.yml` has never run (no tags), so
   there is no artifact to check a digest against. `/security/build` used to send
   readers to look for one; it no longer does.
2. **"Reproduces the deployed bundle byte-for-byte" is a property that has to be
   maintained, not a standing fact.** It holds only while the mirror and the
   deployment are at the same commit. A curated export drifts by default — on
   2026-08-09 the mirror was two weeks behind and its `apps/web` build script was
   missing the prerender step entirely, so a rebuild could not have matched no
   matter how careful the verifier was. Re-check this whenever the deployment
   moves; a stale mirror turns an honest verifier into a false positive.

**Provenance identity in the deployed build.** `scripts/build-manifest.mjs` reads,
in order: `GITHUB_SHA`/`GITHUB_REF_NAME` (the attested release workflow),
`RAILWAY_GIT_COMMIT_SHA`/`RAILWAY_GIT_BRANCH` (the production deploy, injected by
the platform), then `BUILD_COMMIT`/`BUILD_REF`, then `unknown`. The Railway
fallbacks were added after the deployed page shipped reading
`Source commit: unknown` — provenance with no provenance in it, the one field
that makes the digest checkable being the one field missing. No Railway
configuration is required.

## One load-bearing build detail

`apps/web/vite.config.ts` aliases `libsodium-wrappers-sumo` to its CJS build on
purpose: that package's published ESM dist is broken (it imports a file it doesn't
ship), so a browser `import()` of the ESM entry fails to bundle and the deployed app
would never load. It is the **same** libsodium the server loads, so client/server
crypto interop is unchanged. The alias is commented in place — don't remove it; if a
future libsodium release fixes its ESM dist, drop it only after `pnpm --filter
@truecairn/web build` succeeds without it and the CI E2E job stays green.

## The full gate (what CI proves on every push)

Building the client is one step. The complete definition of done (`CLAUDE.md`) is
both CI jobs green:

```bash
pnpm install --frozen-lockfile
pnpm -r typecheck
DATABASE_URL=postgresql://truecairn:truecairn@localhost:5432/truecairn_dev pnpm test
pnpm --filter @truecairn/web build
```

`.github/workflows/ci.yml` runs the full vitest workspace against real Postgres
and the Playwright enrollment E2E on real Chromium (real WASM libsodium). Reproduce
either locally with the commands above; the E2E needs a Chromium (`pnpm --filter
@truecairn/web exec playwright install --with-deps chromium`).
